# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

InstaCaptions: a single-user web app that generates Instagram captions with Claude and publishes them directly, and doubles as the content admin for the owner's portfolio site (javiersabando.lat, repo `portfolio_2026`). Astro 5 (SSR), Vue 3 islands, Tailwind CSS 4, Drizzle ORM + SQLite, Cloudflare R2. Auth is a single password (`APP_PASSWORD`) — no accounts or registration. UI copy and code comments are in Spanish — match that when editing.

The app runs **only locally** (`pnpm dev`); there is no deployment. The README.md is the authoritative setup guide (Meta app config, R2 config, env vars); `docs/meta-instagram-setup.md` covers the Meta app step by step, local HTTPS, and troubleshooting. Read them before touching the Instagram OAuth or storage flows.

## Commands

Package manager is **pnpm** (12 on the dev machine; the project isn't pinned). Native deps (`better-sqlite3`, `sharp`, `esbuild`, `exifreader`, `@tailwindcss/oxide`) must be listed in `pnpm-workspace.yaml` under BOTH `allowBuilds` (`pkg: true`, read by pnpm 12) and `onlyBuiltDependencies` (read by pnpm 10.17), or pnpm skips their build scripts and the bindings fail at boot (`Could not locate the bindings file`, which the dev server reports as `MiddlewareCantBeLoaded`). After adding one, run `pnpm rebuild <pkg>`.

| Command | Purpose |
| --- | --- |
| `pnpm dev` | Dev server at https://localhost:4321 (self-signed HTTPS) |
| `pnpm build` | Production build to `dist/` |
| `pnpm start` | Run the build (`node ./dist/server/entry.mjs`) |
| `pnpm db:generate` | Generate a migration after editing `src/db/schema.ts` |
| `pnpm db:studio` | Drizzle Studio to inspect the DB |
| `pnpm astro check` | Type-check (`@astrojs/check` + strict tsconfig; also covers `scripts/`) |
| `pnpm backfill:image-facts [--apply]` | Fill `width`/`height`/`color`/`takenAt` on older portfolio docs (dry-run by default) |

There is no test suite or linter configured. Type checking via `astro check` is the only automated verification.

## Architecture

**Request lifecycle.** `src/middleware.ts` runs on every request. Auth is single-user: a session cookie derived from `APP_PASSWORD` + `SESSION_SECRET` (`src/lib/session.ts`, the sha256-token pattern the old portfolio_2025 admin used; constant-time compares; changing the password invalidates the session). `context.locals.user` is always the fixed owner user (`src/lib/ownerUser.ts`: first row of the `user` table, created if the DB is fresh — keeps existing FKs and the `u/{userId}/` storage namespace working). The middleware guards `/app/*` and `/api/*` (redirect to `/login` for pages, `401 JSON` for API); `/api/login` is the only open API route (rate-limited 5/15min per IP). Logout: `POST /api/logout`. **Because the middleware guarantees auth, API routes use `context.locals.user!.id` directly without re-checking.**

**Database is a module side-effect.** Importing `src/lib/db.ts` opens the SQLite file (creating `./data/` if needed), sets WAL, and runs pending migrations from `src/db/migrations` immediately. Migrations apply automatically on every boot — there is no separate migrate step.

**Schema lives in one file.** `src/db/schema.ts` holds the app tables (`user`, `instagramAccount`, `scheduledPost`, `generationLog`) plus `session`/`account`/`verification`, which are legacy from the removed Better Auth setup — kept to avoid a migration, no longer used. The `user` table now holds a single owner row (see `ownerUser.ts`). After any change here, run `pnpm db:generate` to produce a migration; do not hand-edit migrations. Timestamps are `integer({ mode: "timestamp" })` and booleans `integer({ mode: "boolean" })` to keep the schema portable for a future Postgres migration (see README).

**Three external-service wrappers in `src/lib/`** — keep all third-party calls inside these, API routes orchestrate them:
- `instagram.ts` — **Instagram API con Instagram Login** (not Facebook Login). Graph calls hit `graph.instagram.com/v23.0` via `graphFetch`, which throws `MetaApiError`. **`err.isAuthError` (code 190) means an expired token** → routes return `409 { error: "reconnect" }` and the UI prompts to reconnect. OAuth: authorize at `instagram.com/oauth/authorize` (scopes `instagram_business_basic,instagram_business_content_publish`) → `exchangeCodeForToken` POSTs to `api.instagram.com` and returns `igUserId` directly (no Facebook-page discovery) → `exchangeForLongLivedToken`/`refreshLongLivedToken` hit `graph.instagram.com`. The 60-day token auto-refreshes in the scheduler (`refreshExpiringTokens`, checked every 6h) when it expires within 7 days.
- `claude.ts` — Anthropic SDK (`MODEL = "claude-sonnet-4-6"`, `maxRetries: 3`). `generateCaptions` enforces a strict JSON-only system prompt and **retries once on malformed JSON** (separate from the SDK's network retries). Throws `CaptionGenerationError` with `reason: "parse" | "api"`. Images are normalized to 768px JPEG before sending (Claude bills by pixel dimensions); raw input caps are 8MB from the library and 15MB for IG downloads. `/api/captions/generate` is rate-limited per user (20/hour, in-memory `src/lib/rateLimit.ts`).
- `storage.ts` — Cloudflare R2 via the S3 SDK. **Every key is namespaced under `u/{userId}/`** and every client-supplied path goes through `sanitizeRelPath` (rejects `.`/`..`) — preserve this isolation when adding storage operations. Folders are emulated S3 prefixes with marker objects. Private bucket: previews and Instagram's image fetch both use short-lived presigned URLs.

**Portfolio manager.** `/app/portfolio` + `/api/portfolio/*` manage the content of the separate portfolio site (javiersabando.lat / `portfolio_2026` repo: a static Astro site that reads this Mongo only at build time, so edits go live after «Publicar sitio» — see Publish below). Single-user app: any valid session is the owner, so these routes are covered by the normal auth guard. Four dedicated lib modules, deliberately separate from the Instagram ones:
- `portfolioDb.ts` — native `mongodb` driver (lazy connect on first use, NOT at import) against the portfolio's Mongo (`PORTFOLIO_MONGODB_URI`), collection `images`. The doc shape lives in `portfolioSchema.ts` (Zod, source of truth of the contract; portfolio_2026 reads it in `src/content.config.ts` with its own Zod and silently skips docs that don't match — change both sides in the same change). `upsertImage` validates fields against the schema and enforces the invariants no route can skip: `category` derived (always `categories[0]`) and inserts with `visible: false` (review rule). Mongoose isn't used here, so every upsert sets `updatedAt` in `$set` and `createdAt` + defaults in `$setOnInsert` manually.
- `portfolioStorage.ts` — second S3 client for the portfolio's PUBLIC R2 bucket (`PORTFOLIO_R2_*` env vars). Global keys + public URLs (`publicUrl()`/`keyFromPublicUrl()` against `PORTFOLIO_ASSETS_BASE_URL`), unlike `storage.ts` which enforces `u/{userId}/` + presigned URLs. Never mix the two. `sessionFromKey()` derives the session from `blog/images/{session}/{file}`.
- `portfolioOriginals.ts` — third S3 client, for the PRIVATE bucket of full-res originals (`PORTFOLIO_ORIGINALS_BUCKET`, same `PORTFOLIO_R2_*` credentials, so the token needs both buckets). Base for a future photo store. It only has `putOriginal`/`deleteOriginal`/`presignOriginal` + `originalKeyFor()` (same path as the public WebP, with the original's extension) and **never builds public URLs**. If the env var is missing, uploads simply skip the original.
- `portfolioImage.ts` — `extractExif()` (exifreader, must run on the ORIGINAL buffer: sharp strips metadata; also `takenAt` from DateTimeOriginal, stored as the camera's wall-clock time in UTC), `toWebp()` (≤2560px, q80), `imageFacts()` (visible width/height + **average** color — not sharp's `dominant`, which comes out near-black on photos with shadows) and `analyzeImageFromUrl()` (one download → exif + facts).
Pipeline:
1. **Upload** (`api/portfolio/upload.ts`), in order:
   - EXIF from the original → WebP → facts.
   - Public PutObject (required).
   - Original to the private bucket (best-effort; reported as `original: stored|not_configured|failed`).
   - **Upsert of the doc** with EXIF + facts + `originalKey` + session (best-effort; inserts are still `visible: false`), so no upload is left orphaned or loses its original.
2. **Generate** (`api/portfolio/generate.ts` → `generatePortfolioMetadata` in `claude.ts`): bilingual caption/footer + categories. Existing Mongo categories are injected as preferred vocabulary, and the call is logged to `generationLog` with `source: "portfolio_image"`.
3. **Save** (`api/portfolio/image.ts`): upsert by unique `url`. The first insert defaults to `visible: false`, so nothing goes live unreviewed.

`api/portfolio/original.ts`: POST attaches an original to an existing doc (rejects `aspect_mismatch` when the aspect ratio differs by more than 2% from the doc's width/height); GET returns a 10-minute presigned URL. `catalog.ts` and `extract-exif.ts` also compute facts. `scripts/backfill-image-facts.ts` runs on Node type stripping, so it imports `src/lib/*.ts` with explicit extensions and must not import modules that read `import.meta.env`. It reads the public URLs, takes a JSON backup in `backups/` (gitignored), never overwrites existing values and doesn't touch `updatedAt`. UI: `PortfolioManager.vue` (browser + upload wizard) and `PortfolioImageForm.vue` (metadata editor + "Original (privado)" section).

Review queue (`/app/portfolio/revisar`, `PortfolioTriage.vue`): keyboard-first curation over the whole `images` collection (Mongo only — works without `PORTFOLIO_R2_*`). `GET api/portfolio/review` returns ALL docs sorted by `url` (client groups by session, derived from the `blog/images/{session}/` key prefix until the `session` field is backfilled); edits go through `PATCH api/portfolio/image` → `updateImageFields` (partial update of an EXISTING doc; 404 if missing — a PATCH never creates stubs, unlike the PUT upsert). Optimistic UI: apply → PATCH → revert only the sent fields on error. Two modes over the same frozen queue: "uno a uno" (keyboard) and "cuadrícula" (multi-select with shift-ranges + bulk visible/portfolio/stars). A *series* (diptych/triptych) is a shared `crypto.randomUUID()` + `order` created from the grid selection; the series panel drag-reorders, propagates the first image's footer to the rest, and undoes (`series: null`).

Sessions (`sessions` collection in the portfolio's Mongo, insta_bot-only — the public site never reads it): one doc per shoot (`{ session, context, createdAt, updatedAt }`), the `context` feeds AI generation. `GET/PUT api/portfolio/sessions` → `listSessions`/`upsertSession`. Session names are R2 key segments, validated by `sessionNameSchema` (`/^[\w-]+$/`). The "Subir sesión" wizard in `PortfolioManager.vue` uploads a whole shoot to `blog/images/{session}/`: saves the session context, then per photo upload (EXIF→WebP→R2) + PUT of the image doc with `session` + EXIF (inserts land `visible: false` as always).

Batch AI cataloging (`portfolioBatch.ts` + `POST/GET api/portfolio/generate-batch`): one in-memory job at a time walks the selected images in chunks of 6-8 inside ONE Claude conversation (`createPortfolioBatchConversation` in `claude.ts` — after each chunk the images are replaced in history by a text summary so past pixels aren't re-billed; style coherence comes from the model seeing its own previous JSON). Images are fetched by PUBLIC URL (works without `PORTFOLIO_R2_*`), series members stay in the same chunk with a "Serie A, posición n de m" note, session `context` and the vocabulary (tags collection + categories in use) go in the first turn. The job only produces proposals (never writes Mongo); logs to `generationLog` with `source: "portfolio_batch"`. UI: "✨ Generar metadata" in the grid's bulk bar → `PortfolioBatchReview.vue` polls the job and shows side-by-side accept/reject per field; out-of-vocabulary categories come unchecked with a "nueva" badge — approving one saves it on the image AND `POST api/portfolio/tags` adds it to the vocabulary.

Vocabulary CRUD (`/app/portfolio/tags`, `PortfolioTags.vue`): two-level tag hierarchy over the `tags` collection, plus health views. `GET api/portfolio/tags` returns `{ tags, usage }` (usage = per-category counts from `images`, via `categoryUsageCounts`). Rename/merge (`PUT { from, to, apply }` → `renameCategoryEverywhere`) rewrites `categories` (preserving position, deduping) and recomputes the derived `category` on EVERY affected image — `apply:false` is a dry-run returning `{ affected, merged }` so the UI confirms with the count before touching anything; if `to` already exists it's a merge. Deleting a tag (`deleteTag`) leaves the images untouched (category becomes an orphan). Hierarchy moves (`PATCH { name, parent }` → `setTagParent`) enforce strictly two levels (parent must be a root, a tag with children can't be nested). All tag reads/writes use a case-insensitive collation (locale es, strength 2) so pre-migration mixed-case names like "Paisaje" don't spawn duplicates. Orphan categories (used but not in `tags`) get an "adoptar" action; unused tags get delete.

Posts (`/app/portfolio/blogs`, `portfolioBlogDb.ts` + `portfolioBlogSchema.ts`, `api/portfolio/blogs.ts`/`blog.ts`/`blog-assist.ts`): CRUD of the `blogs` collection — articles (`type: "blog"`) and projects (`type: "repo"`) — with ordered content blocks (`contentBlockSchema`; image blocks carry `size: normal|ancho|completo`). insta_bot owns the invariants the old Mongoose hooks enforced: unique slugs (`slug.ts`; a manual slug that already exists → `slug_taken`) and `publishedAt` set the first time a post becomes `published`. The AI assists (`generateBlogFieldSuggestion`, `generateBlogImageCaption` in `claude.ts`) only suggest; the editor decides what to save.

Collections (`/app/portfolio/colecciones`, `portfolioCollectionsDb.ts`, `api/portfolio/collections.ts`/`collection.ts`; shape in `collectionInputSchema`): curated photo essays with es/en title and intro, a cover and an ordered list of photo URLs. The site builds only `published: true` collections and, inside them, only `visible: true` photos (consecutive photos of one series are grouped in a row).

Publish (`portfolioPublish.ts` + `api/portfolio/publish.ts`, `PortfolioPublish.vue` bar on the portfolio, posts and collections pages): the portfolio site (portfolio_2026) is static and reads Mongo only at build time, so changes go live after a new build. POST calls the Vercel Deploy Hook (`PORTFOLIO_DEPLOY_HOOK_URL`, secret; rate-limited 1/min) and stores `lastPublishedAt` in `site_meta` (`{ _id: "publish", lastPublishedAt, changedAt }`); GET counts images/blogs/collections with `updatedAt` after it. Deletes and vocabulary edits leave no `updatedAt`, so they call `markSiteChanged()` (portfolioDb.ts) to set `changedAt` — call it from any new write path that changes the public site without touching `updatedAt`.

**Two core flows** (the app's reason to exist):
- *Flow A — existing posts* (`source: "existing_post"`): read recent IG media, generate captions, copy to clipboard. Instagram's API cannot edit published captions, so the UI links out to paste manually.
- *Flow B — publish* (`source: "new_post"`): upload/pick an image → generate → publish. `api/instagram/publish.ts` creates a media container, then **polls `getContainerStatus` (up to 20×1.5s) until `FINISHED`** before calling publish — Instagram processes images asynchronously.

Every generation is recorded in `generationLog` (source, context, tone, options, chosen index) to iterate on the prompt later.

**Frontend pattern.** `.astro` pages under `src/pages/app/` are thin shells that render Vue islands with `client:load`. The Vue components (`src/components/vue/`) are self-contained: they fetch their own data from `/api/*` endpoints rather than receiving server props. `src/lib/tones.ts` is intentionally server-dependency-free so both the API and Vue components can import the `TONES` list.

## Conventions

- API routes return JSON via a local `json(body, status)` helper and use **string error codes** (`reconnect`, `not_connected`, `claude_unavailable`, `container_failed`, …) that the Vue layer maps to Spanish messages. Follow this instead of inventing prose errors server-side.
- All env access goes through `import.meta.env.*` (Astro), declared in `src/env.d.ts` — add new vars there and to `.env.example`.
- IDs are `crypto.randomUUID()`; timestamps are JS `Date` (Drizzle handles the integer conversion).
